## 1. 试听规则：前后端一致性

**规则**（已批准）：试听免费——TRIAL 预约不得创建付费订单；不创建零金额订单替代；历史 TRIAL 付费订单不迁移不回写；**「每生每师限一次试听」本轮明确不实施**，保留为待产品负责人确认的独立规则。

前后端两层一致落地，互为冗余（前端隐藏入口是体验，服务端闸门是权威）：

| 层 | 位置 | 行为 |
|---|---|---|
| 服务端闸门 | `order/app/OrderApplicationService.createForCaller` | TRIAL 预约下单抛 `IllegalStateException` → 全局映射 **409**，文案「试听课免费，不产生付费订单；如需继续学习请预约正式课」（状态检查在前、类型闸门在后，不改变 FORMAL 既有路径） |
| 服务端视图 | `orderableLessonsForCaller` | 可下单课程列表**服务端排除 TRIAL**（`.filter(b -> "FORMAL".equals(b.type()))`），不依赖前端隐藏 |
| 视图契约 | `BookingOrderView` / `UpcomingBookingView` / `UpcomingLessonView` / `OrderableLessonView` | 全部补 `type` 字段，前端可区分试听/正式（服务端吐真值，不做前端类型推断） |
| 前端 | `student-dashboard.component.html` CONFIRMED 行三支渲染 | 有订单 → 支付状态 pill；`type === 'TRIAL'` → 「免费试听」pill（**无下单按钮**）；否则 → 下单按钮。`student-dashboard.component.ts` 三个 signal 与两个 http.get 泛型同步加 `type` |

**真实服务实证**（本轮新 jar，非仅测试断言）：学生 13900000002 对其 TRIAL 预约下单 → `409 {"detail":"试听课免费，不产生付费订单；如需继续学习请预约正式课"}`；`orderable` 返回 0 条（TRIAL 被排除 + 既有 FORMAL 已有一课一单）；`upcoming-lessons` 12 行全部含 `type`。浏览器走查见 §6。

⚠️ 排查插曲（如实记录）：首次 API 探测观察到 400「Idempotency-Key 必须为 UUIDv4 格式」——是探测脚本用 `uuid.uuid4().hex`（无连字符）所致，非业务闸门缺陷；改用 `str(uuid.uuid4())` 后即得 409。幂等键格式校验先于业务校验属预期分层。

## 3. 改期校验

**规则**（已批准）：改期目标档期必须尚未开始（与新建预约同一时间语义）；**源预约时间不限制**——已开始/已过去的 CONFIRMED 课仍可改到未来（改期核心补救价值）；不加改期次数/课前时限等新规则；保留「先锁新档期再释放旧档期」事务顺序。

实现（`booking/app/BookingApplicationService.reschedule`）：`holdSlot(newSlotId)` 之后、`releaseSlot(slotId)` 之前校验 `newSlot.getStartAt().isBefore(now)` → `IllegalArgumentException`（→400「不能改期到已过去的时段」）；校验失败事务回滚自动释放新档期，原档期未被释放而保留。

测试：
- `BookingRescheduleIT` +2：①改期到过去档期 400 → 断言原档期保持（再改期成功证明）→ pastSlot/slot1 回 OPEN、slot2 HELD（证明回滚释放）；②JdbcTemplate 将源档期回拨到过去 → 已开始课程的改期到未来 200 成功（补救场景受保护）。
- 单测 `BookingApplicationServiceTest.pastTargetSlotRescheduleRejected`：400 + `verify(never()).releaseSlot(any())` + slotId 不变；setUp 补 `futureSlot` 桩对齐新契约（mock 修的是返回值非断言，无断言弱化）。

## 4. 并发改期：复现、根因与验证（结论：无需修复）

任务书要求不得仅凭加注解宣称并发已解决、必须真实事务竞争验证。执行路径：先根因分析，再写**真实并发** IT 实证。

- **根因**：`AvailabilitySlot` 有 `@Version` 乐观锁，`Booking` 无；但并发改期共享同一旧档期（第二个到达的 `releaseSlot(旧slotId)` 会更新同一行），旧档期释放构成天然**串行化点**——败者在 flush 时 0 行更新 → `OptimisticLockException` → 事务整体回滚（含其 HELD 的新档期）→ **孤儿 HELD 状态在结构上不可达**。
- **实证**：新建 `RescheduleConcurrencyIT`，`@RepeatedTest(3)`：CyclicBarrier 两线程对**同一预约**并发改期到档期 B/C（各自真实 `mvc.perform` 走完整 HTTP→事务→提交链路，非顺序模拟），断言：成功数 ≥1；败者状态 ≥400；最终预约档期 ∈{B,C}；**A/B/C 三档期中恰一个 HELD、其余全 OPEN**（无孤儿）。3 轮全绿。
- **否决**：给 `Booking` 加 `@Version`——未证实必要且扩大改动面（写入 `docs/DECISIONS.md`）。

## 5. 课程定价正数校验

决策分析标记 🟡 的疑缺陷确认属实：`SubjectOffering` 构造器无价格校验（仅 `reprice` 有）。最小修复：构造器加 `if (pricePerHourCents <= 0) throw new IllegalArgumentException("课时定价必须为正数（单位：分）")`，新增与调价路径约束一致。`SubjectIdempotencyIT` +1 用例：0 / -100 → ≥400，20000 → 201。

## 7. 是否动了资金核心逻辑：**否**

## 8. 退款结算红冲：根因与方案（仅方案，未实施）

**根因**（已核查代码）：结算条目 `PENDING→SETTLED→PAID_OUT` 的 `markSettled`/`markPaidOut` **零调用**；支付成功生成条目后终身 PENDING；退款 `executeForBookingCancellation`/`executeArbitration` 退钱包、关订单，**不触碰结算条目**——退款后教师侧仍挂着该课的课酬条目（含平台抽成），仲裁文案「结算条目作废」与代码不符。现有防护良好面：`ux_refund_cases_order`（V7，order_id 唯一）已排除同一订单双重退款。

**方案**（`docs/PRODUCT_DECISIONS_PENDING.md` §9，九步实施含 V11 迁移细节）：推荐**红冲负向条目**方向——`entry_kind` EARNING/REVERSAL + `reverses_entry_id` + 部分唯一索引 `ux_settlement_reversal … WHERE entry_kind='REVERSAL'`（一课至多一红冲）；SETTLED/PAID_OUT 不可「作废」只能红冲对冲。**当前零代码改动，待负责人批准**（四项待确认：红冲方向/部分退款比例规则/存量数据订正/是否作为提现上线前置——建议作为提现功能上线的前置条件）。
