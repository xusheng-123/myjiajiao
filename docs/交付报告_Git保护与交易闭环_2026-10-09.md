## 一、Git 版本保护（第一阶段）

此前项目**没有任何版本控制**——所有进度只存在于文件系统，一次误删即永久丢失，这是上一轮交付报告中明确标注的最大结构性风险。本轮已消除：

### 1. 建立了什么

| 项 | 内容 |
|---|---|
| 本地 Git 仓库 | 4 个提交：版本基线 `9631f8d`（480 个文件）→ G3 `7979522` → G7 `3f6da7d` → 文档同步 `0555311` |
| .gitignore | 排除依赖目录、构建产物、日志、数据库备份、部署包、密钥文件、运行期上传文件 |
| 凭据核查 | 配置文件中所有密钥均为「环境变量注入 + 开发占位默认值」结构，**仓库内无任何硬编码真实凭据**（核查过程与报告均未展示具体值） |

### 2. 刻意保留与刻意排除的

- **保留版本管理**：`.env.example` 等不含真实敏感信息的配置模板正常入库——它们是新环境部署的操作说明。
- **排除**：`.env` 及一切环境密钥文件、`backend/data/files/`（用户上传的资质材料等运行期数据，之后新上传自动忽略；历史上已入库的测试文件不影响恢复能力）。
- **未做且未经授权不会做**：添加远程仓库、推送、公开。当前恢复能力 = 本地提交历史本身；若需要异地容灾（防机器盘故障），由负责人决定是否提供远程仓库。

### 3. 恢复方式（已写入交接文档，此处摘要）

- 查看历史：`git log --oneline`；查看某版本文件：`git checkout <提交号> -- 路径`

- 危险操作白名单外一律禁止（reset --hard / clean -fd / 强制推送），该纪律已写入交接文档与团队规则。

## 二、G3 —— 学生「确认监护绑定」入口（第二阶段）

### 问题

平台规定：家长必须先与学生建立监护关系、**学生本人确认**后才能代付下单、查看周报。但此前学生端没有任何界面能看到「有人申请绑定我」——新家庭注册后闭环卡死在学生这一步，只能靠运营后台手工处理。

### 实现

- **后端**：新增一个只读接口 `GET /parent/me/children:pending`——仅学生本人可调用（角色护栏 + 只返回发给自己的申请），返回申请方称呼与关系，最少信息、不暴露家长任何敏感数据。确认动作**完全复用**既有接口（该接口无参数、按登录者身份查询，结构上不存在越权空间），零逻辑改动。
- **前端**：学生工作台新增「监护绑定申请」卡：显示「某某（父亲）申请与你建立监护关系」+ 一键确认按钮；防重复点击；结果提示以服务端响应为准。

### 验收证据

| 层 | 结果 |
|---|---|
| 集成测试 | 新增用例：学生 A 可见本人申请、学生 B 列表为空（对象级隔离）、教师访问被拒(403)、他人确认不消耗 A 的申请、重复确认拒绝且无重复副作用 |
| E2E | 全新账号走完整链路 9 项断言全过（发起→可见→隔离→确认→清空） |
| 浏览器走查 | 家长发起 → 学生端出现申请卡 → 点击确认 → 提示「已确认绑定：对方现在可以为你的课程代付下单，并查看你的学习周报」→ 家长端刷新显示「已生效 ✔」 |

## 三、G7 —— 学生/家长「下单 + 支付」界面（第三阶段）

这是资金闭环最后一块、也是此前对真实用户完全不可见的缺口：后端下单/支付 API 早已完整并经安全实测，但界面上学生不知道要付钱、家长没法付钱。

### 实现

**学生端（只下单，不收款）**
- 课程表中「导师已确认」的课程行出现「下单」按钮；下单后显示服务端返回的金额与「◷ 待支付」状态；已支付显示「✓ 已支付」。
- 下单成功后的提示如实引导：「当前版本由家庭统一支付，请家长在家长端为该课程完成支付」。

**家长端（选孩子 → 下单 → 支付）**
- 新增「课程与订单」卡，四步闭环：
  1. 从「已生效」绑定的孩子中选择一位；
  2. 「查看可下单课程」——只列出导师已确认且尚未生成订单的课程，**金额为服务端定价快照**（前端不计算一分钱）；
  3. 一键下单，订单进入家庭订单列表（付款方视角）；
  4. 待支付订单出现支付入口。

**支付入口的环境区分（本轮重点守住的红线）**

| 环境 | 界面行为 |
|---|---|
| 沙箱开放（联调/演示） | 显示「沙箱演示支付」按钮，支付成功提示**明确标注「模拟渠道，非真实收款」** |
| 生产配置（沙箱关闭） | **不显示任何在线支付按钮**，改为「线下收款：转账后由运营确认（模式 B）」引导，与运营后台已有的收款确认界面（上一轮 G1）衔接 |

- 是否显示沙箱按钮由**服务端配置接口**决定（前端无法自行开启），并已用生产配置实际重启验证：配置返回关闭、沙箱端点确已下线。

### 刻意不做的（诚实边界，请负责人知悉）

1. **未接入任何真实支付渠道**（微信/支付宝/银联）——需要商户资质，属既定决策项，本轮绝不越线。所有演示均为沙箱模拟，界面措辞与报告措辞一致。
2. **学生端没有支付按钮**——学生钱包没有充值通道，若开放支付必然「下单容易付款死路」。学生自建的订单保持待支付，由家长支付或运营线下确认（该失败路径已被自动化测试证实为安全回滚，不会产生坏状态）。
3. **未改动任何支付状态机、数据库迁移、资金联动规则**——本轮全部是「给已验证的后端能力补界面」，新增代码仅 3 个只读/配置查询接口。

### 验收证据

| 层 | 结果 |
|---|---|
| 集成测试（新增 OrderPaymentFlowIT） | 可下单视图含服务端定价；无关家长/学生越权均 403；一课一单重复下单 409；付款方数据隔离（学生订单家长不可见，反之亦然）；**钱包余额不足时支付失败且订单安全回滚**；支付成功联动（订单已付+钱包扣减）；已付订单不可重复发起支付 |
| E2E（新增 27 项断言） | 全新三账号走完整链路：绑定→可下单视图→学生下单→payer 隔离→重复下单 409→无余额支付被拒→家长充值→家长下单→沙箱支付→PAID→钱包扣减准确→已付防重复 |
| 浏览器走查 | 学生为数学课下单 ¥200.00（服务端价）→ 家长查看可下单课程只剩物理课 ¥300.00（已被下单的自动消失）→ 下单 → 充值 ¥1000 → 沙箱演示支付 → 订单「✓ 已支付」、钱包余额 ¥700、充值/扣款两条流水入账 → 学生端对同一课程再点下单被服务端 409 拒绝并原样展示原因 |

## 五、过程中遵守的关键纪律（对应任务书红线）

- **顺序执行**：先 Git 保护 → G3 全部验证通过后才动 G7，未并行抢跑。
- **先核查再动手**：G3/G7 实施前均重新审计了现有接口契约（未凭历史文档假定），因此 G7 发现了两个规划外事实——①学生自建订单的沙箱支付会因学生钱包无余额失败（据此设计了「学生不下单支付、界面如实引导」的方案）；②「可下单课程」视图确实缺失（补了最小只读端点）。
- **不掩盖问题**：沙箱支付在全部界面与文案中标注为模拟；生产模式冒烟中发现沙箱端点下线后返回 500 而非 404（全局异常处理器包装所致，功能正确），已如实记录而非修饰。
- **零危险操作**：全程未执行任何 reset/clean/强推；未添加远程；未展示任何凭据值。
