## 一、根因分析：汇总为什么会少算

`SettlementApplicationService.summaryOf` 原实现用**同一条分页查询**同时承担两个职责：

```java
// 修复前（缺陷代码）
var entries = settlementRepository.findByTeacherIdOrderByCreatedAtDesc(teacherId, PageRequest.of(0, 50));
long pending = entries.stream().filter(e -> e.getStatus() == PENDING).mapToLong(SettlementEntry::getNetCents).sum();
```

- 汇总（`pendingNetCents`/`paidOutNetCents`）只对**前 50 条明细**求和；
- 明细列表本身分页 50 条是合理的 UI 约束，但汇总被同一截断连带；
- 教师条目超过 50 条后，第 51 条起的课酬**静默消失在汇总里**。

**实际影响（主库实证）**：教师 13900000001 有 84 条 PENDING 条目，全量净额 ¥18,105.00；修复前 API 只报前 50 条之和 ¥11,220.00，**少报 ¥6,885.00**（少算 40.4%，条目数越多少算越多）。

**为什么测试没抓住**：此前所有结算断言都用 ≤50 条的数据集，截断缺陷在 50 条以内不可见。

## 二、修复逻辑：汇总与明细拆成两个独立查询

**方案**：DB 端 SUM 聚合（非应用内存累加），SQL：

```java
@Query("select coalesce(sum(e.netCents), 0) from SettlementEntry e "
        + "where e.teacherId = :teacherId and e.status = :status")
long sumNetCentsByTeacherIdAndStatus(UUID teacherId, SettlementStatus status);
```

- `summaryOf` 对 PENDING、PAID_OUT 各调一次聚合（走既有索引 `ix_settlement_teacher(teacher_id, status)`），明细仍用原 `PageRequest.of(0, 50)` 查询；
- **没有删除分页限制**——明细保持 50 条上限，只有汇总改为全量；
- SETTLED 状态当前不计入任何展示字段：`markSettled`/`markPaidOut` 在生产路径零调用，SETTLED 不可达，该语义已在代码 javadoc 中如实注明（未来红冲实施时须按批准语义调整本查询）；
- DTO 结构不变（`pendingNetCents`/`paidOutNetCents`/`entries`），**前端零改动**。

## 三、分页如何保持

明细列表仍是 `findByTeacherIdOrderByCreatedAtDesc(teacherId, PageRequest.of(0, 50))`——浏览器走查实证教师仪表盘明细恰好渲染 50 行（84 条总条目）。汇总数字与明细条数自此互不依赖。
